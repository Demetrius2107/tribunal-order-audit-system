## 三、执行步骤（按依赖排序）

### 第 1 步：明确主线，固化现状（0 天）

- **动作**：以 README「0806 版本概览」为地图，确认主线六模块为准；空壳模块（inventory-push / finance-settlement）明确忽略
- **验收**：能随时说清每个模块属于主线/支线/占位，以及当前在哪一步

### 第 2 步：R1 合并共享内核（约 1 周）—— 唯一值得先做的重构

- **目标**：三份 common 合一为 `tribunal-common-core / -starter / -event`，消除三处重复
- **动作**：
  1. `tribunal-common-core`：ApiResponse / BizException / 工具类统一（纯 Java，不依赖 Spring）
  2. `tribunal-common-starter`：AuthInterceptor / FeignConfig / MybatisPlusConfig 自动装配，服务只需引入 starter
  3. `tribunal-common-event`：跨系统事件契约类（OrderApprovedEvent 等）
  4. 更新所有服务 pom.xml 引用新 common，删除旧 common
- **验收**：`mvn clean test` 全量通过，无旧 common 引用遗留
- **验收结果（2026-08-07 完成）**：✅ 全量通过（15 模块 BUILD SUCCESS）
  - `tribunal-common-core`：ApiResponse/BizException/CustomerCreditDto + 库存/金融 DTO 统一于包 `com.demetrius.tribunal.common`（OMS 9 服务 import 零改动）
  - `tribunal-common-starter`：auth 鉴权（JWT 解析/RBAC 注解/拦截器/Feign 内部 Token）+ MybatisPlus（分页/乐观锁）自动装配，消除 9 处重复 MybatisPlusConfig
  - `tribunal-common-event`：IntegrationEvent 契约 + OrderApproved/BillStatusChanged/InventoryChanged 事件 record（M3 填充字段）
  - BizException 默认码统一为 `500000`（原 push=`INV-999`/settlement=`FIN-999`）
  - 顺带修复预先缺陷：`OrderReviewApplicationServiceTest` 漏 mock `occupyCredit`（信用占用 F-403 后加未同步，与 R1 无关）
  - ⚠️ 遗留：旧 common 目录 + 9 处 MybatisPlusConfig 待物理删除（删除命令被拒未执行；不影响构建，旧 common 已从 reactor 移除，MybatisPlusConfig 被 starter `@ConditionalOnMissingBean` 兜底）
- **风险**：依赖替换可能遗漏 → 全量编译兜底验证
- **为什么先做**：它是所有后续工作的地基，现在每加一个功能都要在三处同步改 ApiResponse/BizException，越拖越痛

### 第 3 步：M3 异步化（约 2 周）—— 最高价值

- **目标**：审单从"同步调 5 个服务"变为"同步 3 子域 + 发事件即返回"，解决审单 RT 长、补偿复杂
- **动作**：
  1. 引入 Kafka + 本地消息表 `t_outbox_message`（业务操作 + 消息发布原子性）
  2. billing / fulfillment 从 Feign 同步改 Kafka 事件消费（= 重构阶段 R3）
  3. 消费失败重试 3 次，超限进死信队列，对账任务兜底
  4. 同一 orderId 事件用 orderId 做 partition key，保证顺序消费
  5. 清掉 `BillStatusCallbackApplicationService`、`OrderStatusRecordListener` 的 TODO
- **验收**：审单接口不再同步等待 billing/fulfillment；outbox 表积压可控（PENDING > 100 告警）
- **验收结果（2026-08-07 完成）**：✅ 全量通过（15 模块 BUILD SUCCESS，67 测试全绿）
  - **本地消息表**：`t_outbox_message` + `OutboxMessagePo`/`OutboxMessageMapper` + `OutboxRelayTask`（@Scheduled 5s 轮询，指数退避 2s/4s/8s，超 3 次标记 FAILED）
  - **事件发布改造**：`OrderEventPublisher` 从裸 `kafkaTemplate.send` 改为写 outbox（事务性发布），partition key = orderId（顺序消费）
  - **approve() 重构**：移除 billing/fulfillment Feign 同步调用，通知移出补偿 try-catch（非关键路径），事件写入 outbox 与订单确认同事务
  - **billing-service**：新增 `OrderEventConsumer`（消费组 billing-service，消费 OrderApproved 生成账单）+ `BillingEventPublisher`（发布 billing-events 回传状态）+ `BillStatusCallbackListener` 从 Feign 改 Kafka 发布
  - **fulfillment-service**：新增 `OrderEventConsumer`（消费组 fulfillment-service，消费 OrderApproved 创建履约单）
  - **order-service**：新增 `BillingEventConsumer`（消费 billing-events 驱动状态机，替代 Feign 回调）
  - **Kafka 错误处理**：`KafkaErrorHandlingAutoConfiguration`（common-starter 自动装配，指数退避重试 3 次 + 死信队列 DLT，所有消费服务自动获得）
  - **清理 TODO**：`BillStatusCallbackApplicationService`（消息队列化已完成）、`OrderStatusRecordListener`（operator 来源已明确）、`OrderReviewApplicationService`（类文档更新）
- **依赖**：第 2 步（common-event 契约类）

### 第 4 步：M4 业务补全（约 3 周）—— 纯功能增值

- **目标**：拆单/合单、寻源分仓、促销/折扣/押金引擎（配置化）
- **动作**：按《OMS核心业务开发指南-拆单寻源状态机》施工图纸
  1. 订单状态机补全：部分发货/部分签收/父订单聚合状态
  2. 寻源分仓：收货地址 + 库存 + 时效 → 最优仓库
  3. 拆单/合单：子订单独立状态机 + 独立履约单，父订单 = 聚合状态
  4. 促销引擎：满减/折扣/买赠，可配置，支持叠加/互斥 + 优惠分摊
- **验收**：对应需求编号（F-310/F-311/F-312、F-201~F-206）在《需求编号与代码实现映射表》从 ⬜ → ✅

## 五、执行原则

1. **一次只做一个主线步骤**，每步有独立验收标准，验收通过才进下一步
2. **功能开发优先于架构调整**——R1 是唯一例外（它是地基，必须先行）
3. **里程碑完成后回填映射表**：把《需求编号与代码实现映射表》对应行状态改为 ✅，形成进度清单
4. **个人项目边界**：不追求 4 系统独立部署 + 全套可观测；主线闭环（下单→审单→账单→履约→回传）+ 架构成立即可
5. **每步收尾提交一次**：按 Conventional Commits（`feat(scope)` / `refactor(scope)`），一个提交只做一件事
