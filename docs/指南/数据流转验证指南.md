# 数据流转验证指南

> 你的问题："写完代码后怎么验证数据流转是正常的？难道手动扮演各个角色吗？"
> 答案：写一个 .http 脚本，按业务流程顺序自动调 API，脚本替你扮演各个角色。

---

## 1. 四层验证策略

| 层级 | 验证什么 | 工具 | 现状 | 投入 |
|------|---------|------|------|------|
| **第 1 层：单元测试** | 领域逻辑正确性（状态机、金额计算、信用校验） | JUnit5 + Mockito | 已有 18 个 | 已完成 |
| **第 2 层：单服务集成** | 单个服务内 Controller → Service → Repository 链路 | @SpringBootTest + H2 | 缺 | 中等 |
| **第 3 层：链路脚本** | 多服务间数据流转（下单→审单→账单→履约） | .http 脚本（IDEA HTTP Client） | **本指南提供** | 低 |
| **第 4 层：手动端到端** | 完整业务场景跑通 | Apifox / Postman | 按需 | 高 |

**你现在最需要的是第 3 层。** 第 1 层你已经有，第 2 层可以后续补，第 4 层偶尔做。

### 2.3 服务端口和启动顺序

| 启动顺序 | 服务 | 端口 | 说明 |
|----------|------|------|------|
| 1 | auth-service | 8087 | 认证服务，其他服务依赖 JWT |
| 2 | customer-service | 8081 | 客户信用 |
| 3 | inventory-service | 8083 | 库存管理 |
| 4 | marketing-service | 8084 | 价格计算 |
| 5 | billing-service | 8082 | 账单 |
| 6 | fulfillment-service | 8085 | 履约 |

| 8 | order-service | 8080 | 订单服务（最后启动，它依赖上面所有服务） |
| 9 | inventory-push-service | 8090 | 库存推送（独立，不阻塞主链路） |
| 10 | finance-settlement-service | 8091 | 金融结算（独立，不阻塞主链路） |
| 11 | task-service | 8088 | 定时任务（可选） |

**快速验证服务是否启动成功：**

```bash
# 批量检查所有服务心跳
for port in 8080 8081 8082 8083 8084 8085 8086 8087 8090 8091; do
  echo -n "Port $port: "
  curl -s -o /dev/null -w "%{http_code}" http://localhost:$port/api/orders/heartbeat 2>/dev/null || \
  curl -s -o /dev/null -w "%{http_code}" http://localhost:$port/api/customers/heartbeat 2>/dev/null || \
  curl -s -o /dev/null -w "%{http_code}" http://localhost:$port/api/inventory/heartbeat 2>/dev/null || \
  curl -s -o /dev/null -w "%{http_code}" http://localhost:$port/api/bills/heartbeat 2>/dev/null || \
  curl -s -o /dev/null -w "%{http_code}" http://localhost:$port/api/fulfillments/heartbeat 2>/dev/null || \
  curl -s -o /dev/null -w "%{http_code}" http://localhost:$port/api/auth/heartbeat 2>/dev/null || \
  curl -s -o /dev/null -w "%{http_code}" http://localhost:$port/api/v1/inventory/heartbeat 2>/dev/null || \
  curl -s -o /dev/null -w "%{http_code}" http://localhost:$port/api/v1/settlement/heartbeat 2>/dev/null || \
  echo "FAIL"
  echo ""
done
```

每个服务返回 200 就表示启动成功。

## 3. 使用 .http 脚本

### 3.1 文件位置

```
docs/api-test/审单链路验证.http
```

### 3.2 使用方法

1. 在 IDEA 中打开 `docs/api-test/审单链路验证.http` 文件
2. 每个请求前面有一个绿色三角 ▶，点击即可执行
3. **按顺序从上到下执行**，不要跳步——每一步的输出是下一步的输入
4. 脚本会自动传递变量（如 orderId、token），你不需要手动复制粘贴

### 3.3 脚本包含 5 个场景

| 场景 | 验证什么 | 步骤 |
|------|---------|------|
| **场景一：正常审单** | 下单→审单通过→各服务数据变化 | 步骤 0-22 |
| **场景二：审单拒绝** | 下单→审单拒绝→信用是否释放 | 步骤 23-26 |
| **场景三：取消订单** | 下单→审单通过→取消→信用+库存是否释放 | 步骤 27-31 |
| **场景四：库存推送** | 模拟上游系统推送库存数据 | 步骤 32-33 |
| **场景五：金融结算** | 扣款→分账→幂等验证 | 步骤 34-36 |

## 4. 验证 Checklist

### 4.1 场景一：正常审单流程

每一步执行后，检查返回值：

| 步骤 | API | 期望返回 | 如果不对 |
|------|-----|---------|---------|
| 1. 登录 | POST /api/auth/login | code=200, accessToken 非空 | 检查 auth-service 是否启动，用户是否注册 |
| 2. 创建库存 | POST /api/inventory/items | code=200, skuCode=SKU-001 | 检查 inventory-service 数据库连接 |
| 4. 查客户信用 | GET /api/customers/.../credit | creditLimit=100000 | 检查 customer.sql 是否执行 |
| 6. 下单 | POST /api/orders | code=200, orderId 非空 | 查看 order-service 日志，Feign 调用是否成功 |
| 8. 查客户信用(下单后) | GET /api/customers/.../credit | creditUsed > 0 | 下单时应该已调用 customer 占用信用 |
| 9. 审单通过 | POST /api/orders/.../review | code=200 | 查看 order-service 日志，五合一编排是否报错 |
| 10. 查订单(审单后) | GET /api/orders/{id} | status=CONFIRMED | 如果不是 CONFIRMED，审单可能失败了 |
| 11. 查库存(审单后) | GET /api/inventory/items/SKU-001 | lockedQuantity > 0 | 审单时应该已调用 inventory 预占 |

### 4.2 数据库验证（可选，更深入）

脚本跑完后，直接查数据库验证数据一致性：

```sql
-- 1. 订单表：应该有 3 条订单（1 通过 + 1 拒绝 + 1 取消）
USE tribunal_order;
SELECT id, order_no, status, total_amount FROM t_order ORDER BY create_time DESC LIMIT 5;

-- 2. 客户表：信用占用应该 = 场景一的订单金额（场景二三已释放）
USE tribunal_customer;
SELECT id, customer_code, name, credit_limit, credit_used FROM t_customer WHERE id = 'cust-001';

-- 3. 库存表：预占数量应该 > 0
USE tribunal_inventory;
SELECT sku_code, sku_name, total_quantity, locked_quantity FROM t_inventory_item;

-- 4. 账单表：应该有账单记录
USE tribunal_billing;
SELECT id, source_order_no, status FROM t_bill ORDER BY create_time DESC LIMIT 5;

-- 5. 履约表：应该有履约记录
USE tribunal_fulfillment;
SELECT id, source_order_no, status FROM t_fulfillment ORDER BY create_time DESC LIMIT 5;
```

## 5. 数据流转检查点

这是最关键的部分——**每一步调用后，哪些服务的数据应该发生变化**：

```
步骤 6: 下单
  ├── order-service:   t_order 插入一条记录，status=TO_BE_CONFIRMED
  └── customer-service: t_customer.credit_used += 订单总额（Feign 同步调用）

步骤 9: 审单通过
  ├── order-service:    t_order.status 改为 CONFIRMED
  ├── customer-service: 信用校验通过（不改变数据）
  ├── inventory-service: t_inventory_item.locked_quantity += 订单数量（库存预占）
  ├── marketing-service: 重新计价（可能调整价格，不持久化）
  ├── billing-service:   t_bill 插入一条记录（Feign 同步调用）
  └── fulfillment-service: t_fulfillment 插入一条记录（Feign 同步调用）

步骤 24: 审单拒绝
  ├── order-service:    t_order.status 改为 REJECTED
  └── customer-service: t_customer.credit_used -= 订单总额（信用释放）

步骤 29: 取消订单
  ├── order-service:    t_order.status 改为 CANCELLED
  ├── customer-service: t_customer.credit_used -= 订单总额（信用释放）
  └── inventory-service: t_inventory_item.locked_quantity -= 订单数量（库存释放）
```

**如果某一步的数据没有变化，说明那一步的 Feign 调用失败了。** 查看 order-service 的日志，搜索 ERROR 或 Exception。

## 6. 常见问题排查

### 6.1 下单返回 500

```
原因：customer-service 没启动，Feign 调用失败
排查：curl http://localhost:8081/api/customers/heartbeat
解决：启动 customer-service
```

### 6.2 审单返回 500 但下单成功

```
原因：五合一编排中某个环节失败
排查：查看 order-service 控制台日志，搜索最近一条 Exception
常见原因：
  - inventory-service 库存不足（先执行步骤 2 创建库存）
  - billing-service 没启动
  - fulfillment-service 没启动
  - marketing-service 没启动（取价失败）
```

### 6.3 客户信用 credit_used 没变化

```
原因：下单时 Feign 调 customer-service 的 occupyCredit 失败了
排查：查看 order-service 日志中的 Feign 调用日志
      查看 customer-service 日志是否有异常
解决：确保 customer-service 启动且数据库连接正常
```

### 6.4 库存 locked_quantity 没变化

```
原因：审单时 Feign 调 inventory-service 的 reserve 失败了
排查：
  1. 确认 inventory-service 启动（curl http://localhost:8083/api/inventory/heartbeat）
  2. 确认库存项已创建（步骤 2-3）
  3. 查看 order-service 日志中的 inventory Feign 调用
```

### 6.5 Kafka 相关错误

```
现象：order-service 日志报 Kafka 相关异常
原因：Kafka 没启动
解决：
  # 检查 Kafka 是否在运行
  curl http://localhost:9092  # 不返回内容但连接成功说明在跑
  
  # 如果没启动，用 Docker 快速启动
  docker run -d --name kafka -p 9092:9092 \
    -e KAFKA_NODE_ID=1 \
    -e KAFKA_PROCESS_ROLES=broker,controller \
    -e KAFKA_LISTENERS=PLAINTEXT://:9092,CONTROLLER://:9093 \
    -e KAFKA_ADVERTISED_LISTENERS=PLAINTEXT://localhost:9092 \
    -e KAFKA_CONTROLLER_LISTENER_NAMES=CONTROLLER \
    -e KAFKA_CONTROLLER_QUORUM_VOTERS=1@localhost:9093 \
    -e KAFKA_INTER_BROKER_LISTENER_NAME=PLAINTEXT \
    -e KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR=1 \
    -e KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR=1 \
    -e KAFKA_TRANSACTION_STATE_LOG_MIN_ISR=1 \
    -e CLUSTER_ID=MkU3OEVBNTcwNTJENDM2Qk \
    apache/kafka:latest
```

### 6.6 "Connection refused"

```
原因：目标端口的服务没启动
排查：确认对应端口的服务已启动
  netstat -ano | findstr :8080  (Windows)
  lsof -i :8080                  (Linux/Mac)
```

## 7. 后续怎么加自动化（第 2 层集成测试）

当你验证完链路没问题后，可以考虑补集成测试，让验证更自动化：

### 7.1 加 H2 测试依赖

在需要集成测试的模块 pom.xml 中加：

```xml
<dependency>
    <groupId>com.h2database</groupId>
    <artifactId>h2</artifactId>
    <scope>test</scope>
</dependency>
```

### 7.2 写集成测试

```java
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)
class OrderControllerIntegrationTest {

    @LocalServerPort
    int port;

    @Autowired
    TestRestTemplate restTemplate;

    @Test
    void shouldCreateOrder() {
        // 构造请求
        var request = new OrderCreateRequest("cust-001", List.of(...), ...);
        
        // 调 API
        var response = restTemplate.postForEntity(
            "http://localhost:" + port + "/api/orders",
            request,
            ApiResponse.class
        );
        
        // 验证
        assertThat(response.getStatusCode()).isEqualTo(HttpStatus.OK);
        assertThat(response.getBody().getCode()).isEqualTo(200);
    }
}
```

### 7.3 测试配置文件

在 `src/test/resources/application-test.yml` 中：

```yaml
spring:
  datasource:
    url: jdbc:h2:mem:testdb;MODE=MySQL
    driver-class-name: org.h2.Driver
    username: sa
    password:
```

集成测试**不需要启动其他服务**——Mock Feign 客户端或者用 @MockBean。它只验证"单个服务内部从 Controller 到数据库的链路是否通"。

## 8. 总结：你的验证工作流

```
写完一个功能
  │
  ├── 第 1 步：跑单元测试（mvn test）
  │   └── 验证领域逻辑正确
  │
  ├── 第 2 步：启动所有服务，跑 .http 脚本
  │   └── 验证多服务间数据流转正确
  │
  ├── 第 3 步：查数据库确认数据一致性
  │   └── 验证最终落库结果正确
  │
  └── 第 4 步（可选）：写集成测试
      └── 让验证自动化，以后改代码不用手动跑
```

**不需要每次都手动扮演各个角色。** .http 脚本就是你的"自动化演员"——它替你登录、下单、审单、查数据。你只需要点绿色三角，看返回值是否符合预期。
