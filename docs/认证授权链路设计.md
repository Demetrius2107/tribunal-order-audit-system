# 认证授权链路设计（auth-service + 全服务鉴权）

> **项目**：tribunal-order-audit-system — B2B 订单审单系统
> **定位**：认证（Authentication，你是谁）+ 授权（Authorization，你能做什么）的全链路落地
> **覆盖需求**：F-901（用户/角色/权限）、N-401（认证）、N-402（授权）
> **文档配套**：《需求编号与代码实现映射表》三、3.9 系统管理域 / 二、N-401/N-402 行

---

## 一、设计目标与安全威胁

| 目标 | 防什么 |
|---|---|
| 密码安全 | 数据库被拖库后密码不泄露（BCrypt 加盐哈希） |
| 登录防爆破 | 弱口令被暴力尝试（失败锁定） |
| 接口越权 | 经销商调用审单/结算接口（RBAC 权限校验） |
| Token 泄露 | Token 长期有效（双 Token 短时效 + 轮换） |
| 线程串号 | 线程池复用导致 A 用户操作 B 用户订单（ThreadLocal 必须清理） |

**优先级**：认证 > 授权 > 易用性。订单系统里"越权"与"串号"是后果最严重的两类漏洞。

## 二、认证（Authentication）

### 1. 密码存储：BCrypt

- 注册时 `BCryptPasswordEncoder.encode(rawPassword)` 加盐哈希，库中只存密文（`t_user.password`）
- 登录时 `matches(rawPassword, cipher)` 校验
- BCrypt 内置盐与成本因子（默认 10，约 100ms），暴力破解成本高

### 2. 登录失败锁定（防爆破）：LoginFailGuard

```
同一用户名连续失败 maxFailures(默认5) 次 → 锁定 lockMinutes(默认15) 分钟
登录成功 → 清除失败计数
```

- 单实例内存实现（ConcurrentHashMap），生产换 Redis（INCR + TTL），见「生产化演进」

### 3. 双 Token（Access + Refresh）

| Token | 时效 | 携带内容 | 用途 |
|---|---|---|---|
| Access Token | 2h（`jwt.access-expiration-ms`） | userId/username/roleCode/**permissions** | 业务接口鉴权 |
| Refresh Token | 7d（`jwt.refresh-expiration-ms`） | 仅身份标识（tokenType=refresh） | 换取新双 Token |

**关键设计**：
- Access Token 短时效 → 泄露影响面小
- Refresh Token **轮换**（`RefreshTokenStore.issue` 先吊销该用户全部旧 refresh）→ 防重放：旧 refresh 一旦被使用立即作废
- **类型隔离**：`validateTokenOfType` 强制校验 `tokenType` 声明，refresh token 冒充 access token 调业务接口会被拒绝（`JwtTokenParser.parseAccessToken` 同样校验）
- 登出：`POST /api/auth/logout` 吊销该用户全部 refresh token；access token 靠 2h 过期自然失效

### 4. 密码与校验细节

- 密码校验失败与用户不存在的报错文案**保持一致**（"用户不存在或密码错误"）——防止通过响应差异枚举用户名
- 注册成功后自动签发双 Token（免二次登录）

## 三、授权（Authorization）：RBAC

```
用户(User) ──1:N──> 角色(Role) ──N:M──> 权限点(Permission)
                                   权限码如: order:review / order:cancel / finance:settle
```

### 1. 数据模型（docs/sql/auth.sql）

| 表 | 说明 |
|---|---|
| `t_user` | 用户，含 `role_code`（单角色简化） |
| `t_role` | 角色（DEALER 经销商 / SALES 销售 / FINANCE 财务 / ADMIN 管理员） |
| `t_permission` | 权限点（15 个：order:create/cancel/modify/review/view、customer:credit、inventory:manage/reserve、billing:settle、finance:settle、marketing:price、fulfillment:ship、notification:send、auth:user/permission） |
| `t_role_permission` | 角色-权限 N:M 关联（ADMIN 全量，DEALER 仅 order:create/cancel/view） |

### 2. 权限注入链路（无状态鉴权的核心）

```
登录/刷新
  └─> AuthApplicationService.issueTokens
        ├─ permissionRepository.findByRoleCode(roleCode)  # 查角色权限
        └─ jwtProvider.generateAccessToken(..., permissions)  # 权限写入 JWT claims
```

下游服务**不查权限中心、不调 auth-service**，只本地解析 Token 的 permissions claims 即可鉴权（大厂网关模式同理）。权限变更后需重新登录（或刷新）生效——因为权限固化在 Token 里，时效 2h。

### 3. 接口级鉴权

```java
@PostMapping("/{orderId}/review")
@RequirePermission("order:review")   // 声明所需权限，任一满足即可
public OrderResult review(...)
```

- 未标注注解的接口：仅要求登录（有有效 Token）
- 无权限返回 403 "无权限执行该操作"

## 四、鉴权过滤器链路（服务端落地）

```
请求 → AuthInterceptor.preHandle
       ├─ 非 Controller 方法（静态资源）→ 放行
       ├─ X-Internal-Token == auth.internal-token（服务间 Feign）→ 记为 internal 用户放行
       ├─ 无 Authorization: Bearer → 401
       ├─ Token 解析失败/过期/类型非 access → 401
       ├─ 写 UserContext（ThreadLocal：userId/username/roleCode/permissions）
       ├─ 方法有 @RequirePermission → 权限比对 → 无权限 403
       └─ 通过 → Controller（业务代码从 UserContext 取当前用户）
请求结束 → afterCompletion → UserContext.clear()  // ★防线程池串号
```

### 共享组件（tribunal-common-starter 自动装配，各服务引入即生效）

| 组件 | 职责 |
|---|---|
| `JwtTokenParser` | 本地解析 Access Token（只解析不签发），校验 tokenType=access |
| `AuthInterceptor` | HandlerInterceptor，上图中的完整链路 |
| `@RequirePermission` | 接口级权限注解 |
| `UserContext` | ThreadLocal 当前用户：`getRequiredUserId()` / `hasPermission()` |
| `FeignInternalTokenInterceptor` | 服务间 Feign 调用自动附加 `X-Internal-Token` 头 |
| `AuthAutoConfiguration` | 自动注册拦截器（白名单默认放行 `/api/auth/**`、心跳；`auth.enabled=false` 可关） |

### 服务间互信（Feign 调用不被拦截）

场景：order-service 审单时 Feign 调 billing/inventory/customer/fulfillment/notification。这些接口已被拦截器保护，若不带凭据会 401。

解决：**内部调用令牌**——所有服务配置相同的 `auth.internal-token`，Feign 请求自动带 `X-Internal-Token` 头，下游校验一致即放行（记为 `internal` 用户）。外部请求者拿不到该令牌（需从配置/环境变量获取），与用户 JWT 隔离。

### 白名单

| 路径 | 原因 |
|---|---|
| `/api/auth/**` | 登录/注册/刷新/登出/校验/权限查询自身 |
| `/**/heartbeat` | 运维探活 |
| `auth.white-list` 追加 | 自定义（如支付回调等外部回调接口） |

## 六、联调用例（curl）

> 前提：已执行 `docs/sql/auth.sql`（含权限点与角色权限种子数据）；按《架构总览》启动 auth(8087)/order(8080) 等服务。

### 1. 注册（DEALER 角色，只有 order:create/cancel/view）

```bash
curl -X POST http://localhost:8087/api/auth/register \
  -H "Content-Type: application/json" \
  -d '{"username":"dealer01","password":"123456"}' \
  -d 'roleCode=DEALER'
# 返回：
# {"success":true,"data":{"token":"<access>","refreshToken":"<refresh>",
#   "userId":"...","username":"dealer01","roleCode":"DEALER",
#   "permissions":["order:create","order:cancel","order:view"]}}
```

### 2. 登录（错误密码触发失败锁定）

```bash
curl -X POST http://localhost:8087/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"dealer01","password":"wrong"}'
# → {"success":false,"code":"800002","message":"用户不存在或密码错误"}
# 连续 5 次后：
# → {"success":false,"code":"800004","message":"登录失败次数过多，账号已锁定，请稍后再试"}
```

### 3. 带 Token 调订单接口（有权限 → 200）

```bash
curl -X POST http://localhost:8080/api/orders \
  -H "Authorization: Bearer <access>" \
  -H "Content-Type: application/json" \
  -d '{"customerId":"c1","skus":[{"skuCode":"SKU001","skuName":"瓶装啤酒","quantity":120,"price":3.5}]}'
# → 200，订单创建成功（DEALER 拥有 order:create）
```

### 4. 无权限角色调审单（DEALER 无 order:review → 403）

```bash
curl -X POST http://localhost:8080/api/orders/{orderId}/review \
  -H "Authorization: Bearer <dealer的access>" \
  -H "Content-Type: application/json" \
  -d '{"approved":true}'
# → 403 {"success":false,"code":"403","message":"无权限执行该操作"}
```

### 5. 未带 Token → 401

```bash
curl http://localhost:8080/api/orders
# → 401 {"success":false,"code":"401","message":"未登录或 Token 缺失"}
```

### 6. Access 过期后用 Refresh 轮换

```bash
curl -X POST "http://localhost:8087/api/auth/refresh?refreshToken=<refresh>"
# → 新双 Token（旧 refresh 立即作废，再次用旧 refresh 刷新 → 800005）
```

### 7. 登出（吊销该用户全部 refresh）

```bash
curl -X POST "http://localhost:8087/api/auth/logout?refreshToken=<refresh>"
```

### 8. 服务间 Feign 调用（自动带 X-Internal-Token，无需手工）

order-service 审单时自动调 inventory/billing/fulfillment/notification——`FeignInternalTokenInterceptor` 自动附加内部令牌，下游放行；**外部调用者不知道 `auth.internal-token`，无法伪装内部服务**。

## 七、生产化演进（当前实现 → 大厂级）

| 项 | 当前实现 | 生产级方案 |
|---|---|---|
| 失败锁定/Refresh 存储 | 单实例内存（ConcurrentHashMap） | Redis：`INCR + EXPIRE` 计数 / `SET refreshToken userId EX 7d`，多实例共享 |
| JWT 密钥 | 各服务 yml 配置 `jwt.secret`（环境变量 `JWT_SECRET` 可覆盖） | 密钥管理服务（KMS/Vault），定期轮换；非对称 RS256 签名 |
| Token 吊销 | Access 靠过期，Refresh 可吊销 | 登出时 Access 进 Redis 黑名单直到过期 |
| 验证码 | 预留（未实现） | 登录/注册图形验证码，防机器人 |
| 数据权限 | 未做（仅接口级功能权限） | 部门/数据范围：本部门、本部门及以下、全部 |
| 审计日志 | 未做 | 登录成功/失败、权限拒绝、敏感操作记录（对接 ES） |
| 密码策略 | 长度不限 | 复杂度校验 + 密码历史（禁复用旧密码） |
| 多端会话 | RefreshTokenStore 按用户吊销 | 设备维度管理：多端登录、互踢、异地登录告警 |
