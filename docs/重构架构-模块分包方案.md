# 重构架构 — 模块分包方案

> **文档定位**：基于"4 大系统 + 共享内核"设计，给出具体的 Maven 模块划分、包结构、迁移映射和部署架构。
> **前置文档**：《目标系统架构设计文档》（设计原则与通信模式）、《订单业务全系统功能清单》（19 系统全景）

---

## 一、设计原则

| 原则 | 含义 | 具体表现 |
|------|------|----------|
| **同领域同步 → 同进程子模块** | 审单时同步调用的 customer/inventory/marketing，从独立微服务降为 OMS 内部 Maven 子模块 | 3 个独立服务 → 3 个子模块，去掉网络开销 |
| **跨领域异步 → 独立微服务** | OMS 与履约/结算之间通过 Kafka 事件解耦，各自独立部署 | 4 个 JVM，4 个数据库 |
| **DDD 四层标准化** | 每个微服务内部按 domain → application → infrastructure → api 组织 | 领域层零框架依赖 |
| **共享内核统一抽取** | 3 份 common 合并为 1 份，全局共享 | 11 份重复配置 → 1 份自动装配 |

## 三、各系统模块详解

### 3.1 共享内核 tribunal-common

| 模块 | 职责 | 来源 |
|------|------|------|
| common-core | ApiResponse、BizException、ErrorCode 枚举、金额工具、日期工具 | ← tribunal-order-common |
| common-event | 跨系统事件契约类（OrderApprovedEvent、OrderShippedEvent 等） | 新建 |
| starter-auth | JWT 验证拦截器、RBAC 权限码解析、@RequirePermission 注解 | ← tribunal-order-common (AuthInterceptor) |
| starter-feign | Feign 全局超时（connect 2s / read 5s）、重试（3 次）、熔断（Resilience4j） | ← tribunal-order-service (FeignRetryConfig) 升级 |
| starter-mybatis | MyBatis-Plus 配置、分页插件、乐观锁插件、自动填充 | ← 各服务 MybatisPlusConfig 合并 |

**依赖规则**：所有系统都依赖 common-core + common-event；可部署微服务额外依赖需要的 starter。

### 3.2 库存中心 tribunal-inventory-center

| 模块 | 职责 | 来源 |
|------|------|------|
| domain | StockItem 聚合根、可售库存计算公式、预占/释放领域逻辑 | 新建 |
| application | 库存查询、批量预占、释放、库存预警用例编排 | 新建 |
| infrastructure | MyBatis Repository 实现、Kafka 消费上游库存变更事件 | 新建 |
| api | REST Controller（库存查询/预占/释放）、Feign 接口暴露给 OMS | 新建 |
| push | 多协议上游数据接入（HTTP 接口、MQ 消费、SFTP 文件解析） | ← tribunal-inventory-push-service |

**核心变化**：现有 inventory-push 只做数据接入，新增的 core 模块补全了可售库存计算、预占释放能力。

### 3.3 OMS 订单中台 tribunal-oms

| 模块 | 职责 | 来源 |
|------|------|------|
| domain | Order 聚合根、OrderStatus 状态机、领域事件定义 | ← tribunal-order-service (domain 层) |
| application | 下单用例、审单用例（同步调 3 子域 + 发 Kafka 事件）、改单/取消用例 | ← tribunal-order-service (application 层) |
| infrastructure | Repository 实现、Feign 客户端（调库存中心）、Kafka 生产者、Redis 幂等 | ← tribunal-order-service (infrastructure 层) |
| api | REST Controller、DTO、Assembler | ← tribunal-order-service (api 层) |
| customer | Customer 聚合、信用额度管理、信用占用/释放、客户分级 | ← tribunal-order-customer-service |
| inventory | 可售库存视图（本地缓存）、预占请求 DTO、库存校验逻辑 | ← tribunal-order-inventory-service |
| marketing | 价格计算引擎、促销规则匹配、优惠分摊、押金规则 | ← tribunal-order-marketing-service |
| auth | JWT 签发、Refresh Token 轮换、RBAC 权限码管理、用户/角色/权限 CRUD | ← tribunal-order-auth-service |
| channel | 多渠道订单接入（B2B 门户、API 对接、文件导入）、订单格式归一化 | ★新建 |
| notification | 短信/邮件/站内信发送、通知模板管理、发送记录 | ← tribunal-order-notification-service |
| task | 定时任务（超时自动取消、自动审单、日终对账、状态同步） | ← tribunal-order-task-service |

**核心变化**：
1. customer/inventory/marketing 从独立微服务降为 OMS 内部子模块，去掉 Feign 网络调用，改为进程内方法调用
2. auth/notification/task 同理合并，共享 OMS 的数据库和 Spring Boot 进程
3. 审单编排从"同步调 5 个服务"变成"同步调 3 个子域 + 发 2 个 Kafka 事件"
4. billing 移到金融结算系统，fulfillment 移到履约系统

### 3.4 履约系统 tribunal-fulfillment

| 模块 | 职责 | 来源 |
|------|------|------|
| domain | FulfillmentOrder 聚合根、履约状态机（待处理→拣货中→已出库→运送中→已签收） | ← tribunal-order-fulfillment-service (domain 层) |
| application | 履约创建用例、拣货下发、发货确认、签收回传用例 | ← tribunal-order-fulfillment-service (application 层) |
| infrastructure | Repository 实现、Kafka 消费 order-events、发布 delivery-events | ← tribunal-order-fulfillment-service (infrastructure 层) |
| api | REST Controller、DTO | ← tribunal-order-fulfillment-service (api 层) |
| orch | 履约调度：拆单（多仓/多商家）、寻源分仓（按地址/库存/时效）、下发策略 | ← tribunal-order-fulfillment-service (业务逻辑) + 新建 |
| wms | 仓储管理：收货入库、上架、拣货分配、波次管理、复核出库 | ★新建 |
| tms | 运输管理：承运商选择、路由规划、运单管理、轨迹追踪、签收确认 | ★新建 |

**核心变化**：现有 fulfillment-service 只有简化的发货指令，新增 wms 和 tms 补全仓储和运输能力。OMS 审单通过后发 `OrderApprovedEvent`，履约系统异步消费创建履约单。

### 3.5 金融结算 tribunal-settlement

| 模块 | 职责 | 来源 |
|------|------|------|
| domain | Bill 聚合根、SettlementOrder 聚合根、结算状态机 | ← tribunal-finance-settlement-service (domain 层) |
| application | 计费用例、扣款用例、分账用例、退款用例、对账用例 | ← tribunal-finance-settlement-service (application 层) |
| infrastructure | Repository 实现、Kafka 消费 order-events/delivery-events、支付渠道 SDK 对接 | ← tribunal-finance-settlement-service (infrastructure 层) |
| api | REST Controller、DTO | ← tribunal-finance-settlement-service (api 层) |
| bms | 计费系统：费用明细拆解（商品/运费/优惠/税费/佣金/手续费）、账单生成 | ← tribunal-order-billing-service |
| payment | 支付网关：微信/支付宝/银联对接、幂等扣款、支付状态轮询 | ★新建 |
| core | 结算中心：多方分账（平台/商家/物流/分销商）、退款冲正、T+N 结算打款、日终对账 | ← tribunal-finance-settlement-service (核心业务) |
| invoice | 发票管理：开票申请、电子发票生成、冲红、发票池管理 | ★新建 |

**核心变化**：现有 billing-service（轻量账单）和 finance-settlement-service（金融结算）合并为一个系统。billing 作为 bms 子模块保留账单生成能力，finance-settlement 拆分为 core（结算）+ 新增 payment（支付）和 invoice（发票）。

## 四、包结构规范

每个微服务内部的 DDD 四层包命名统一如下（以 OMS 为例）：

```
com.tribunal.oms
├── domain                          # 领域层（零框架依赖）
│   ├── order                       #   Order 聚合
│   │   ├── model/                  #     Order 聚合根、OrderItem 实体、值对象
│   │   ├── event/                  #     领域事件（OrderCreatedEvent 等）
│   │   ├── service/                #     领域服务（OrderDomainService）
│   │   ├── repository/             #     Repository 接口（不写实现）
│   │   └── enums/                  #     OrderStatus、OrderType 等枚举
│   └── shared/                     #   共享内核（值对象基类等）
│
├── application                     # 应用层（用例编排）
│   ├── order                       #   订单用例
│   │   ├── cmd/                    #     命令对象（CreateOrderCommand）
│   │   ├── query/                  #     查询对象（OrderQuery）
│   │   ├── OrderApplicationService.java
│   │   └── OrderReviewApplicationService.java
│   └── event/                      #   事件发布（OrderEventPublisher）
│
├── infrastructure                  # 基础设施层
│   ├── repository/                 #   MyBatis-Plus Repository 实现
│   ├── feign/                      #   Feign 客户端（调库存中心）
│   ├── kafka/                      #   Kafka 生产者 / 消费者
│   ├── redis/                      #   Redis 幂等 / 缓存
│   └── config/                     #   配置类
│
├── api                             # 接口层
│   ├── controller/                 #   REST Controller
│   ├── dto/                        #   请求 / 响应 DTO
│   └── assembler/                  #   DTO ↔ Domain 转换
│
├── customer                        # 客户子域（独立聚合，同进程）
│   ├── domain/
│   ├── infrastructure/
│   └── api/
│
├── inventory                       # 库存子域
├── marketing                       # 营销子域
├── auth                            # 认证授权
├── channel                         # 渠道接入
├── notification                    # 通知服务
└── task                            # 定时任务
```

**子域模块**（customer/inventory/marketing 等）内部也按 DDD 简化分层，但通常只有 domain + infrastructure 两层，不需要独立的 application 和 api 层（由 OMS 核心的 application 层统一编排）。

## 七、系统间通信矩阵

### Feign 同步调用（同进程内为方法调用，跨进程为 Feign）

| 调用方 | 被调方 | 方式 | 场景 | 超时 |
|--------|--------|------|------|------|
| OMS → customer | 进程内方法调用 | 同进程 | 审单校验客户信用 | - |
| OMS → inventory(子域) | 进程内方法调用 | 同进程 | 审单校验可售库存 | - |
| OMS → marketing | 进程内方法调用 | 同进程 | 审单计算价格/优惠 | - |
| OMS → inventory-center | Feign | 跨进程 | 库存预占（实时确认，防超卖） | connect 2s / read 5s |

### Kafka 异步事件

| 发布方 | Topic | 消费方 | 事件类 | 触发时机 |
|--------|-------|--------|--------|----------|
| OMS | order-events | Fulfillment, Settlement | OrderApprovedEvent | 审单通过 |
| OMS | order-events | Fulfillment, Settlement | OrderCancelledEvent | 订单取消 |
| OMS | order-events | Fulfillment, Settlement | OrderRejectedEvent | 审单拒绝 |
| Fulfillment | delivery-events | OMS, Settlement | OrderShippedEvent | 已发货 |
| Fulfillment | delivery-events | OMS, Settlement | OrderDeliveredEvent | 已签收 |
| Settlement | settlement-events | OMS | SettlementCompletedEvent | 结算完成 |
| Settlement | settlement-events | OMS | RefundCompletedEvent | 退款完成 |
| Inventory Center | inventory-events | OMS | InventoryChangedEvent | 库存变化 |

## 八、事件契约定义

所有跨系统事件定义在 `tribunal-common-event` 模块中：

```java
// OrderApprovedEvent — OMS 发布，Fulfillment + Settlement 消费
public record OrderApprovedEvent(
    String orderId,
    String orderNo,
    String customerId,
    List<OrderItemSnapshot> items,      // 商品快照（SKU/数量/单价）
    BigDecimal totalAmount,
    String shippingAddress,
    LocalDateTime approvedAt
) {}

// OrderShippedEvent — Fulfillment 发布，OMS + Settlement 消费
public record OrderShippedEvent(
    String orderId,
    String fulfillmentOrderNo,
    String carrierCode,                 // 承运商编码
    String trackingNo,                  // 物流单号
    List<ShipmentItem> shippedItems,    // 本次发货明细
    LocalDateTime shippedAt
) {}

// OrderDeliveredEvent — Fulfillment 发布，Settlement 消费（触发结算）
public record OrderDeliveredEvent(
    String orderId,
    String fulfillmentOrderNo,
    String signedBy,                    // 签收人
    LocalDateTime deliveredAt
) {}

// SettlementCompletedEvent — Settlement 发布，OMS 消费
public record SettlementCompletedEvent(
    String orderId,
    String settlementOrderNo,
    BigDecimal settledAmount,
    SettlementType settlementType,      // NORMAL / REFUND
    LocalDateTime settledAt
) {}
```

```

tribunal-common-event        ← common-core

tribunal-starter-feign       ← common-core + spring-cloud-starter-openfeign + resilience4j
tribunal-starter-mybatis     ← common-core + mybatis-plus-boot-starter

tribunal-inventory-center-*  ← common-core + common-event + 需要的 starter
tribunal-oms-*               ← common-core + common-event + 需要的 starter
tribunal-fulfillment-*       ← common-core + common-event + 需要的 starter  （不依赖 oms!）
tribunal-settlement-*        ← common-core + common-event + 需要的 starter  （不依赖 oms / fulfillment!）
```

**关键约束**：
- fulfillment 不依赖 oms 的任何模块（只依赖 common-event 中的事件类）
- settlement 不依赖 oms 和 fulfillment 的任何模块
- oms 依赖 inventory-center-api（Feign 接口），但不依赖 inventory-center 的内部实现
- 所有跨系统通信只通过事件契约（common-event），不直接 import 对方代码

## 十、审单编排改造前后对比

### 改造前（现有架构）

```java
// OrderReviewApplicationService.approve() — 同步调 5 个服务
public void approve(String orderId) {
    // ① 同步调 customer-service（Feign）
    customerFeignClient.occupyCredit(...);
    // ② 同步调 inventory-service（Feign）
    inventoryFeignClient.preOccupy(...);
    // ③ 同步调 marketing-service（Feign）
    marketingFeignClient.calculatePrice(...);
    // ④ 同步调 billing-service（Feign）—— 如果后面失败，这里已生成账单
    billingFeignClient.createBill(...);
    // ⑤ 同步调 fulfillment-service（Feign）—— 如果失败，账单已悬空
    fulfillmentFeignClient.createFulfillment(...);
    // ⑥ 发 Kafka 事件（fire-and-forget，无本地消息表）
    kafkaTemplate.send("order-events", event);
}
```

### 改造后（目标架构）

```java
// OrderReviewApplicationService.approve() — 同步调 3 子域 + 异步发事件
@Transactional
public void approve(String orderId) {
    // ① 同进程调用 customer 子域（信用校验 + 占用）
    customerService.occupyCredit(...);
    // ② 同进程调用 inventory 子域（可售校验）
    inventoryService.checkAvailable(...);
    // ③ Feign 调库存中心（预占——跨进程，需要实时确认）
    inventoryCenterFeignClient.preOccupy(...);
    // ④ 同进程调用 marketing 子域（价格确认）
    marketingService.confirmPrice(...);
    // ⑤ 更新订单状态
    order.approve();
    orderRepository.save(order);
    // ⑥ 写本地消息表 + 发 Kafka 事件（事务内原子）
    outboxRepository.save(new OutboxMessage("order-events",
        new OrderApprovedEvent(orderId, ...)));
    // billing 和 fulfillment 不在这里调——它们异步消费 OrderApprovedEvent
}
```

**改造效果**：
- 同步调用从 5 个减少到 1 个（只有库存预占需要跨进程 Feign）
- 审单方法执行时间从 ~2s 降到 ~200ms（去掉 4 次网络往返）
- 补偿逻辑大幅简化：只有库存预占需要补偿（Feign 调用失败时释放），billing/fulfillment 不在同步链路中
- 本地消息表保证"业务操作 + 事件发布"原子性，解决 fire-and-forget 问题
