## R1：合并共享内核（1 周）

### 目标

把 `tribunal-order-common` + `tribunal-inventory-push-common` + `tribunal-finance-settlement-common` 合并为统一的 `tribunal-common`，消除三份重复的 ApiResponse/BizException/GlobalExceptionHandler。

### 交付物

| 交付物 | 验收标准 |
|--------|----------|
| `tribunal-common-core` 模块 | ApiResponse/BizException/工具类统一，所有服务引用同一份 |
| `tribunal-common-starter` 模块 | AuthInterceptor/FeignConfig/MybatisPlusConfig 自动装配，各服务只需引入 starter |
| `tribunal-common-event` 模块 | 跨系统事件契约类（OrderApprovedEvent 等）定义完成 |
| 所有服务 pom.xml 更新 | 引用新的 common 模块，删除旧 common 依赖 |
| 旧 common 模块删除 | 编译通过，无遗留引用 |

### 关键决策

- common-core 不依赖 Spring（纯 Java）
- common-starter 依赖 Spring，通过 `spring.factories` / `@AutoConfiguration` 自动装配
- common-event 不依赖任何业务模块，只包含事件 DTO 类

### 风险

- 全局替换 common 依赖可能遗漏，需全量编译验证
- GlobalExceptionHandler 合并时注意各服务差异（如 billing 有特殊的账单异常处理）

## R2：OMS 内部子域合并（2 周）

### 目标

把 `customer-service`、`inventory-service`、`marketing-service` 从独立 Spring Boot 服务降级为 OMS 内部的 Maven 子模块。去掉 Feign 调用，改为进程内方法调用。

### 交付物

| 交付物 | 验收标准 |
|--------|----------|
| `tribunal-oms-customer` 子模块 | Customer 领域 + Repository + Service，进程内调用 |
| `tribunal-oms-inventory` 子模块 | Inventory 可售查询 + 预占/释放（注意：这里管的是 OMS 的逻辑库存视图，不是库存中心） |
| `tribunal-oms-marketing` 子模块 | 价格规则 + 促销计算 + 押金计算 |
| OMS 审单编排改造 | `approve()` 中 customer/inventory/marketing 改为进程内调用，不再走 Feign |
| 数据库合并 | customer/inventory/marketing 表合并到 `tribunal_oms` 库 |
| 旧服务模块删除 | customer-service/inventory-service/marketing-service 标记为 deprecated |

### 审单编排变化

```
改造前：
  approve() → Feign → customer-service (8081)
             → Feign → inventory-service (8083)
             → Feign → marketing-service (8084)
             → Feign → billing-service (8082)
             → Feign → fulfillment-service (8085)

改造后（R2 阶段，billing/fulfillment 仍同步）：
  approve() → 进程内 → customer 子域
             → 进程内 → inventory 子域
             → 进程内 → marketing 子域
             → Feign  → billing-service (8082)     ← R3 改异步
             → Feign  → fulfillment-service (8085)  ← R3 改异步
```

### 风险

- 数据库合并需要数据迁移（customer/inventory/marketing 表搬到 oms 库）
- 进程内调用后事务边界变化：原来跨服务各自事务，现在同进程可能需要同一事务

## R3：异步事件改造（2 周）

### 目标

把 billing 和 fulfillment 从 Feign 同步调用改为 Kafka 异步事件消费。引入本地消息表保证"业务操作 + 消息发布"原子性。

### 交付物

| 交付物 | 验收标准 |
|--------|----------|
| `tribunal-common-event` 事件类 | OrderApprovedEvent/OrderShippedEvent/OrderDeliveredEvent 等 |
| 本地消息表 `t_outbox_message` | 建表 + OutboxMessageRepository + 定时发送任务 |
| OMS 事件发布改造 | `approve()` 改为写 outbox 表，异步发送 Kafka 事件 |
| Fulfillment Kafka 消费者 | 消费 OrderApprovedEvent，创建履约单 |
| BMS Kafka 消费者 | 消费 OrderApprovedEvent，生成账单 |
| OMS Kafka 消费者 | 消费 OrderShippedEvent/OrderDeliveredEvent/SettlementCompletedEvent，驱动状态机 |
| 死信队列 | 消费失败 3 次后投递 DLT，有告警 |
| Feign 依赖移除 | OMS 不再 import billing/fulfillment 的 Feign 客户端 |

### 审单编排变化

```
改造后（R3 完成）：
  approve() → 进程内 → customer 子域（信用校验+占用）
             → 进程内 → inventory 子域（库存预占）
             → 进程内 → marketing 子域（价格计算）
             → 写 outbox 表（事务内）
             → 返回（不等下游）

  异步：
    Fulfillment 消费 OrderApprovedEvent → 创建履约单
    BMS 消费 OrderApprovedEvent → 生成账单
```

### 关键决策

- 本地消息表 vs Kafka 事务消息：选本地消息表（实现简单，不依赖 Kafka 事务）
- 事件顺序：同一 orderId 的事件用 orderId 做 partition key，保证顺序消费
- 补偿：异步步骤失败重试 3 次，超限进死信，由对账任务处理

### 风险

- 改异步后，审单通过的下游处理变成最终一致，用户感知有延迟
- 需要监控 outbox 表积压情况

## R4：业务能力补全（3 周）

### 目标

补全 OMS 最核心的业务能力：拆单/合单、寻源分仓、促销引擎。

### 当前进度

| 交付物 | 验收标准 | 状态 |
|--------|----------|------|
| 拆单逻辑 | 按仓库拆分子订单，父子关联，金额按比例分摊（末单吸收尾差） | ✅ 已完成 |
| 寻源分仓 | 按 SKU 逐项选最大库存仓，库存不足抛 `InsufficientStockException` | ✅ 已完成 |
| 父单状态聚合 | 子单发货/签收回传聚合父单状态（SPLITTED→PARTIALLY_SHIPPED→SHIPPED→PARTIALLY_SIGNED→SIGNED） | ✅ 已完成 |
| 合单逻辑 | 同客户同地址同时效的订单合并发货 | ⬜ 未开始 |
| 促销引擎 | 满减/折扣/买赠/第二件半价，可配置，支持叠加/互斥 | ⬜ 未开始 |
| 优惠券管理 | 券模板/发券/用券/核销 | ⬜ 未开始 |
| 押金引擎 | 5 类押金按包装类型配置，参与金额计算 | ⬜ 未开始 |
| 优惠分摊 | 优惠金额按比例分摊到每件商品（支持退货退款） | ⬜ 未开始 |
| 售后退货 | 退货申请→审核→退款→库存回退→信用释放 | ⬜ 未开始 |

> **M4 已完成的三项核心能力**：状态机补全、寻源分仓、拆单（含父单状态聚合），均通过 35 个新增单元测试验证。

### 拆单流程

```
审单通过
  → 寻源分仓（决定每个SKU从哪个仓发）
  → 拆单（不同仓的SKU拆成子订单）
  → 每个子订单独立创建履约单
  → 父订单状态 = 已拆单
```

### 促销引擎设计

```
输入：订单明细 + 客户信息 + 促销规则列表
处理：
  1. 匹配适用的促销规则（按客户/组/SKU组过滤）
  2. 按优先级排序
  3. 互斥规则处理（同类型促销只取最优）
  4. 叠加规则处理（可叠加的促销依次计算）
  5. 折扣上限校验
输出：每件商品的优惠分摊金额 + 订单总优惠金额
```

## R5：微服务治理（2 周）

### 目标

引入 Nacos 服务发现、Resilience4j 熔断降级、Redis 分布式幂等、Spring Cloud Gateway。

### 交付物

| 交付物 | 验收标准 |
|--------|----------|
| Nacos 注册中心 | 所有服务注册到 Nacos，Feign 服务名路由 |
| Feign URL 直连移除 | 所有 `@FeignClient(url=...)` 改为 `name` 路由 |
| Resilience4j 熔断 | 关键 Feign 客户端配置熔断器（失败率 > 50% 触发） |
| Resilience4j 降级 | 非核心服务（通知）配置 fallback |
| Redis 分布式幂等 | 替代进程内 ConcurrentHashMap，SETNX + TTL |
| Redis 登录失败锁定 | 替代进程内 LoginFailGuard |
| Redis Refresh Token | 替代进程内 RefreshTokenStore |
| Spring Cloud Gateway | 统一入口、路由、限流 |
| 配置中心 | Nacos Config，环境隔离 |

### 熔断配置示例

```yaml
resilience4j:
  circuitbreaker:
    instances:
      inventory-center:
        failure-rate-threshold: 50
        slow-call-rate-threshold: 60
        slow-call-duration-threshold: 3s
        wait-duration-in-open-state: 30s
        sliding-window-size: 20
        minimum-number-of-calls: 10
      notification-service:
        failure-rate-threshold: 80
        wait-duration-in-open-state: 10s
```

## R6：可观测与加固（2 周）

### 目标

生产级可观测性：结构化日志、全链路追踪、监控告警、压测验证。

### 交付物

| 交付物 | 验收标准 |
|--------|----------|
| 结构化日志 | JSON 格式，含 traceId/spanId/userId |
| 全链路追踪 | 请求从网关→服务→DB/MQ/Feign 全链路可查 |
| Prometheus 指标 | 业务指标（下单量/审单量/RT）+ 系统指标 |
| Grafana 大盘 | 服务健康/依赖健康/消息积压/库存对账 |
| 告警规则 | RT 升高/错误率/QPS 突降/消息积压 |
| 压测报告 | 下单 P99 < 500ms，QPS ≥ 500 |
| outbox 积压监控 | outbox 表 PENDING > 100 条告警 |

## 阶段依赖关系

```
R1（合并内核）→ R2（子域合并）→ R3（异步改造）→ R4（业务补全）
                                      ↓
                               R5（微服务治理）→ R6（可观测加固）
```

- R1 → R2 → R3 是主线，必须顺序完成
- R4 可以和 R3 后半段并行（业务规则引擎不依赖异步改造）
- R5 可以在 R3 完成后启动（需要 ≥ 2 个独立部署的系统才有意义）
- R6 是最后收尾
