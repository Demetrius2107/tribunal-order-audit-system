# 需求规格说明书（生产级目标）

> **文档定位**：本文档定义一套 B2B 订单审单系统达到**大厂生产级**标准的完整需求，是开发者按图索骥学习与实现的目标清单。
> **阅读方式**：每个章节 = 一类需求；每个需求条目 = 一个可验收的学习/开发目标。实现顺序建议按「学习演进路线」章节执行。
> **术语**：经销商（下单方）、销售（审批方）、下游模块（金融账单/库存物料）、BU（业务单元，规则差异化载体）。

# 第一部分：产品概述与功能需求

## 1. 产品概述

### 1.1 产品定位

面向企业间（B2B）渠道订货场景的订单管理与审单系统：经销商在线下单，销售按规则审单，订单审单后生成金融账单完成财务处理，并回传状态。

### 1.2 核心业务链

```
经销商下单 → 规则校验 → 订单创建 → 销售审单 → 信用/金额校验 → 转单生成账单 → 账单/履约回传 → 终态
                                                              ↘ 通知（邮件/短信/站内信/微信）
```

### 1.3 核心设计原则

| 原则 | 说明 |
|---|---|
| 规则驱动 | 价格、促销、信用、整托等规则可配置，不写死在代码里 |
| 状态机驱动 | 订单状态迁移收敛到状态机，非法迁移拒绝，重复回传幂等 |
| 事件驱动 | 跨域协作（通知/审计/下游触发）通过领域事件解耦 |
| 分层清晰 | 接口层/应用层/领域层/基础设施层职责分离，依赖方向单向 |
| 幂等可靠 | 关键写操作幂等，消息不丢不重，失败可重试可对账 |

## 4. 性能需求

| 编号 | 指标 | 目标值 | 说明 |

| N-101 | 下单接口 RT | P99 < 500ms | 不含跨系统同步等待（异步化后） |

# 第三部分：架构目标与工程质量目标

## 11. 架构目标（生产级微服务形态）

### 11.1 服务划分（按领域）

| 服务 | 职责 | 独立数据库 |
|---|---|---|
| gateway | 统一入口、鉴权、限流、路由 | 无 |
| auth | 认证/授权（JWT/RBAC） | 是 |
| customer-service | 客户/信用/信用组 | 是 |
| order-service | 订单/状态机/审单/转单编排 | 是 |
| marketing-service | 促销/折扣/押金/价格 | 是 |
| inventory-service | 库存物料：主数据/库存账/预占释放/推送上游 | 是 |
| billing-service | 金融账单：账单生成/财务审核/结算核销/对账 | 是 |
| notification-service | 邮件/短信/站内信/微信 | 是 |
| task-service | 定时任务（拆单/对账/归档） | 是 |

### 11.2 服务间协作规范

| 场景 | 方式 | 规范 |
|---|---|---|
| 查询依赖 | 同步调用（Feign/gRPC） | 超时/重试/熔断，跨服务传 TraceId |
| 状态推进 | 异步事件（消息队列） | 事件携带幂等键，消费者去重 |
| 跨服务一致性 | 最终一致 + 对账 | 本地消息表/事务消息 |
| 服务发现 | 注册中心（Nacos） | 服务名路由，去 url 直连 |
| 配置管理 | 配置中心 | 环境隔离（dev/test/prod），密钥加密 |

### 11.3 分层规范（DDD）

```
interfaces → application → domain ← infrastructure
```

- domain：纯业务规则，零框架依赖，聚合/值对象/领域服务/领域事件/仓储接口
- application：用例编排、事务边界、DTO 转换、事件发布
- infrastructure：持久化/消息/缓存/外部调用实现
- interfaces：Controller、参数校验、DTO 转换（最薄）

### 11.4 关键架构决策（ADR 摘要）

| 决策 | 选择 | 理由 |
|---|---|---|
| 分布式事务 | 不用 2PC，用最终一致 + 对账 | 2PC 锁时长、性能差、实现复杂 |
| 状态机 | 领域内收敛，非法迁移拒绝 | 幂等 + 可审计 + 可测试 |
| 幂等 | 幂等键（Redis/唯一约束）+ 状态机守卫双层 | 防重复下单/回调 |
| 库存 | 外部系统为准 + 预占/释放 + 对账 | 不自建库存账本 |
| 消息 | 持久化 MQ，失败重试 + 死信 + 对账 | 不丢不重 |

## 14. 里程碑详述

### M0：架构底座（1 周）

**目标**：可运行的 DDD 分层单体，编译测试全绿。

| 交付物 | 验收标准 |
|---|---|
| Maven 多模块工程（common/domain/application/interfaces/infrastructure） | `mvn clean test` 通过 |
| 领域层纯 Java（Order/OrderStatus/OrderId/OrderSku + Repository 接口） | 领域层零 Spring/MyBatis 依赖（架构测试守护） |
| 统一响应 ApiResponse / 业务异常 BizException / 全局异常处理 | 异常统一转 ApiResponse |
| 建库脚本 + 基础表（t_order/t_order_sku/t_customer） | 表结构符合五、表结构章节 |

**学习要点**：依赖倒置（Repository 接口在 domain，实现在 infra）、值对象/聚合根、状态机枚举（静态块构建迁移表）。

### M1：订单核心闭环（1-2 周）

**目标**：下单 → 状态机流转 → 查询，全链路可跑。

| 交付物 | 验收标准 |
|---|---|
| 下单用例（校验→创建聚合→保存→发布事件） | 下单后状态=待确认，金额正确（F-301） |
| 整托校验（数量 % 整托规格 == 0） | 非整托数量被拒（F-302） |
| 订单状态机完整实现 | 合法迁移通过、非法/重复迁移拒绝（F-304） |
| 状态流水落库 | 每次迁移写 t_order_status_record（F-305） |
| 状态机单元测试 | 合法/非法/重复迁移用例 ≥ 10（Q-201） |

**学习要点**：状态机=幂等（重复回传被拒绝）、聚合行为内聚、单元测试先行。

### M2：审单与跨服务（1-2 周）

**目标**：审单走通，引入三合一编排（客户信用 + 库存预占 + 账单生成）。

| 交付物 | 验收标准 |
|---|---|
| customer-service 独立服务（客户/信用领域） | 独立端口独立库，可单独启动 |
| CustomerFeignClient 跨服务调用 | 审单时正确获取信用（N-207 超时/重试） |
| 审单用例（查信用→校验→状态迁移→事件） | 信用不足拒绝、通过则 CONFIRMED（F-303/F-306） |
| 金额校验（应付 > 0） | 非法金额拒绝 |
| inventory-service 独立服务（物料主数据/库存账/预占释放） | 库存查询/预占/释放接口可用（F-501~F-503） |
| InventoryFeignClient 预占库存 | 审单通过时逐 SKU 预占（F-503） |
| billing-service 独立服务（金融账单/财务审核） | 账单生成/审核/结算接口可用（F-601~F-605） |
| BillingFeignClient 生成账单 + 状态回传 | 审单通过生成账单，结算回传驱动订单状态机（F-605） |

**学习要点**：跨服务边界用 DTO 不用领域对象、Feign 超时重试、三合一编排（信用→库存→账单）、服务独立部署。

### M3：异步与事件（2 周）

**目标**：领域事件改 MQ，通知解耦，消息不丢不重。

| 交付物 | 验收标准 |
|---|---|
| 引入 RabbitMQ，OrderStatusChangedEvent 走 MQ | 消费端幂等去重（N-203/N-304） |
| 通知服务订阅事件（站内信/邮件） | 通知与订单业务解耦（F-601/F-602） |
| 本地消息表/事务消息（下单+发消息原子性） | 消息不丢（N-305） |
| 死信队列 + 重试 | 消费失败重试有上限，超限进死信 |

**学习要点**：事件驱动跨域、消息幂等键、事务消息与最终一致性（N-301~N-306）。

### M4：业务规则引擎（2-3 周）

**目标**：促销/折扣/押金/价格全部配置化。

| 交付物 | 验收标准 |
|---|---|
| 促销引擎（客户型/客户组型+SKU 组） | 促销金额正确（F-201/F-202） |
| 折扣池 + 抵扣信用（100%/40%） | 抵扣后应付正确（F-203/F-204） |
| 押金引擎（5 类按类型配置） | 押金计入金额（F-205） |
| 规则引擎（可配置优先级/开关） | 改配置不发布（N-703） |
| 金额计算单元测试 | 核心规则覆盖率 ≥ 80%（Q-201） |

**学习要点**：策略模式/规则引擎、金额用 BigDecimal、可配置化避免硬编码。

### M5：微服务治理（2-3 周）

**目标**：注册中心 + 网关 + 熔断 + 分布式锁。

| 交付物 | 验收标准 |
|---|---|
| Nacos 注册中心，Feign 服务名路由 | 去 url 直连（N-701） |
| Spring Cloud Gateway（路由/鉴权/限流） | 统一入口，越权 403（N-402） |
| 熔断/降级（Sentinel 或 Resilience4j） | 依赖故障时降级，主流程可用（N-208） |
| Redis 分布式锁替代单机锁（下单/审单/转单） | 多实例下关键操作串行化（N-205） |
| 灰度发布 | 新版本灰度放量可回滚（N-704） |

**学习要点**：微服务治理、分布式锁 vs 单机锁、熔断降级语义。

### M6：可观测与运维（2 周）

**目标**：生产级可观测性与 CI/CD。

| 交付物 | 验收标准 |
|---|---|
| 结构化日志 + TraceId 全链路 | 一次请求日志可串（N-501/N-503） |
| 指标采集（Prometheus）+ 监控大盘（Grafana） | 服务/依赖/消息积压可视（N-502/N-505） |
| 告警规则（RT/错误率/QPS 突降/积压） | 阈值告警可达（N-504） |
| CI/CD（编译→测试→扫描→镜像→灰度） | 全绿才合入，门禁生效（Q-103~Q-104） |
| 压测报告 | P99/吞吐达标（N-101~N-107） |

**学习要点**：可观测三支柱（日志/指标/链路）、CI/CD 门禁、压测与容量评估。

### M7：生产加固（2-3 周）

**目标**：容量、容灾、安全、数据治理。

| 交付物 | 验收标准 |
|---|---|
| 订单分库分表（ShardingSphere，按客户/时间） | 超量数据可水平扩展（N-602） |
| 数据归档 + 备份恢复演练 | 热库性能稳定（N-603/N-604） |
| 安全加固（BCrypt/密钥加密/防重放/审计） | 扫描无高风险（N-401~N-408） |
| 双活/容灾方案 | 可用性 99.95%（N-201/N-202） |
| 全链路对账（本地 vs 账单状态） | 不一致自动告警修复（F-701） |

**学习要点**：分库分表/归档、密钥管理、对账机制、容灾设计。

## 15. 里程碑依赖图

```
M0 → M1 → M2 → M3 → M4
                ↘ M5 → M6 → M7
```

- M0~M4 是**业务与架构**主线（必须顺序完成）
- M5 微服务治理可在 M2 后并行启动（前提：已有 ≥2 个服务）
- M6/M7 是**生产化**收尾（建议在业务主线稳定后做）
