## 二、售后退货模块（AfterSale）

### 2.1 业务设计

**状态机**：

```
PENDING（待审核）
  ├──→ APPROVED（已审核）──→ COMPLETED（已完成，退款+退货入库）
  └──→ REJECTED（已拒绝，终态）
```

**售后类型**：退货退款 / 仅退款

**退款金额分摊规则**：按 SKU 金额占订单总额比例分摊，末行吸收尾差（避免浮点精度导致总和不等）。

### 2.2 代码结构（DDD 四层）

| 层 | 文件 | 职责 |
|----|------|------|
| **领域层** | `AfterSaleStatus` | 状态机枚举 + 迁移校验 |
| | `AfterSaleType` | 售后类型（退货退款/仅退款） |
| | `AfterSaleReason` | 售后原因（质量问题/运输破损/发错货等 7 种） |
| | `AfterSaleItem` | 值对象（SKU + 退货数量 + 退款金额 + 押金退还） |
| | `AfterSale` | 聚合根（退款分摊 + 状态流转） |
| | `AfterSaleRepository` | 仓储接口 |
| **基础设施层** | `AfterSalePo` / `AfterSaleItemPo` | 持久化对象 |
| | `AfterSaleMapper` / `AfterSaleItemMapper` | MyBatis-Plus Mapper |
| | `AfterSaleRepositoryImpl` | 仓储实现 |
| **应用层** | `AfterSaleResult` | 出参 DTO |
| | `AfterSaleApplicationService` | 用例编排（申请→审核→确认收货退款） |
| **接口层** | `AfterSaleController` | 5 个 REST 端点 |
| | `AfterSaleCreateRequest` / `AfterSaleReviewRequest` | 请求 DTO |

### 2.3 库存退货入库扩展

合单完成时需将商品退回仓库，扩展了库存服务的退货入库能力：

| 文件 | 新增方法 |
|------|----------|
| `InventoryItem` | `returnStock()` — 退货入库领域方法（增加总库存，不影响预占） |
| `InventoryApplicationService` | `returnStock()` — 应用层 |
| `InventoryController` | `POST /api/inventory/items/{sku}/return` |
| `InventoryFeignClient` | `returnStock()` — 远程调用 |

### 2.4 REST API

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/aftersales` | 创建售后单 |
| GET | `/api/aftersales/{id}` | 查询售后单详情 |
| GET | `/api/aftersales?orderId=` | 按订单查询售后单 |
| POST | `/api/aftersales/{id}/review` | 审核（通过/拒绝） |
| POST | `/api/aftersales/{id}/confirm` | 确认收货并退款 |

### 2.5 数据库

建表脚本：`docs/sql/aftersale.sql`（`t_aftersale` + `t_aftersale_item`）

## 三、可观测性基础（M6）

### 3.1 设计目标

线上出问题"抓瞎"是最大风险。可观测性三大支柱：**日志 + 链路 + 指标**。

### 3.2 实现内容

| 能力 | 实现 | 关键文件 |
|------|------|----------|
| **结构化日志** | dev 环境控制台可读格式，prod 环境 JSON 格式（logstash-encoder），自动输出 `traceId` | `tribunal-common-starter/src/main/resources/logback-spring.xml` |
| **TraceId 生成** | 每个请求生成/继承 `X-Trace-Id`，注入 MDC | `TraceIdFilter` |
| **跨服务传递** | Feign 调用自动透传 `X-Trace-Id` | `TraceIdFeignInterceptor` |
| **响应追踪** | 每次响应自动回填 `traceId` 到 `ApiResponse` | `ApiResponse`（common-core） |
| **指标采集** | actuator + micrometer-registry-prometheus | 各服务 `pom.xml` + `application.yml` |
| **监控看板** | Docker-Compose 集成 Prometheus + Grafana | `docker-compose.yml` + `docker/prometheus.yml` |

### 3.3 自动配置

在 `tribunal-common-starter` 的 `AutoConfiguration.imports` 注册：

```
com.demetrius.tribunal.common.trace.TraceIdAutoConfiguration
com.demetrius.tribunal.common.trace.TraceIdFeignAutoConfiguration
```

所有依赖 common-starter 的服务自动获得 TraceId 能力，无需额外配置。

### 3.4 指标端点

| 端点 | 用途 |
|------|------|
| `/actuator/health` | 健康检查（K8s 探活） |
| `/actuator/prometheus` | Prometheus 指标采集 |
| `/actuator/metrics` | 指标列表 |
| `/actuator/info` | 应用信息 |

### 3.5 验证方式

```bash
docker-compose up -d          # 拉起 Prometheus + Grafana
# Grafana:       http://localhost:3000 (admin/admin)
# Prometheus:    http://localhost:9090/targets
```

## 四、合单模块（MergeOrder）

### 4.1 业务设计

合单是拆单的对称操作：

| 操作 | 说明 |
|------|------|
| **拆单** | 1 个父单 → N 个子单（按仓库分） |
| **合单** | N 个同收货人订单 → 1 个发货单（减少物流成本） |

**状态机**：

```
CREATED（已创建，待打包）
  ├──→ PACKED（已打包）──→ SHIPPED（已发货）──→ DELIVERED（已送达，终态）
  └──→ CANCELLED（已取消，终态）
```

**业务约束**：

1. 至少 2 个成员订单（1 个订单合单没有意义）
2. 所有成员订单 `customerId` 必须相同（同一收货人）
3. 成员订单状态须为 `CONFIRMED` 或 `TRANSFERRED`（已确认/已转单）
4. 成员订单不可重复

### 4.2 代码结构（DDD 四层）

| 层 | 文件 | 职责 |
|----|------|------|
| **领域层** | `MergeOrderStatus` | 状态机枚举 + 迁移校验 |
| | `MergeOrderItem` | 值对象（来源订单 + SKU + 数量 + 单价 + 小计） |
| | `MergeOrder` | 聚合根（工厂校验 + 状态流转 + 金额计算） |
| | `MergeOrderRepository` | 仓储接口 |
| **基础设施层** | `MergeOrderPo` / `MergeOrderItemPo` | 持久化对象 |
| | `MergeOrderMapper` / `MergeOrderItemMapper` | MyBatis-Plus Mapper |
| | `MergeOrderRepositoryImpl` | 仓储实现（成员订单 ID 从明细去重派生） |
| **应用层** | `MergeOrderResult` | 出参 DTO |
| | `MergeOrderApplicationService` | 用例编排（创建/打包/发货/送达/取消/运费/查询） |
| **接口层** | `MergeOrderController` | 10 个 REST 端点 |
| | `MergeOrderCreateRequest` / `MergeOrderShipRequest` | 请求 DTO |

### 4.3 设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 成员订单关联 | 从明细表 `orderId` 去重派生 | 避免单独建关联表，减少冗余 |
| 明细粒度 | 每条记录 = 来源订单 + 1 个 SKU | 保留订单可追溯性，同一 SKU 来自不同订单分开记录 |
| 退款分摊 | 按 SKU 金额占比，末行吸收尾差 | 避免浮点精度导致总和不等 |
| 合单运费 | 独立字段，合并后重新计算 | 支持合并优惠场景 |

### 4.4 REST API

| 方法 | 路径 | 说明 | 权限 |
|------|------|------|------|
| POST | `/api/merge-orders` | 创建合单 | `merge:create` |
| POST | `/api/merge-orders/{id}/pack` | 打包 | `merge:operate` |
| POST | `/api/merge-orders/{id}/ship` | 发货 | `merge:operate` |
| POST | `/api/merge-orders/{id}/deliver` | 送达 | `merge:operate` |
| POST | `/api/merge-orders/{id}/cancel` | 取消 | `merge:operate` |
| POST | `/api/merge-orders/{id}/shipping-fee` | 设置合单运费 | `merge:operate` |
| GET | `/api/merge-orders/{id}` | 查询合单详情 | `merge:view` |
| GET | `/api/merge-orders?customerId=` | 按客户查询合单列表 | `merge:view` |
| GET | `/api/merge-orders/by-order/{orderId}` | 查询某订单参与的合单 | `merge:view` |

### 4.5 数据库

建表脚本：`docs/sql/merge_order.sql`（`t_merge_order` + `t_merge_order_item`）
