## 一、设计哲学

### 核心原则：三条铁律

| 原则 | 含义 | 对标 |
|------|------|------|
| **同层同步，跨层异步** | 同一系统内部的子域用 Feign 同步调用；跨系统用 Kafka 事件异步通信 | 京东 OMS 内部同步，OMS→WMS 异步 |
| **跨层无代码依赖** | 下游系统不 import 上游系统的代码，只依赖 `common-event` 中的事件契约类 | 阿里 DDD 限界上下文隔离 |
| **数据所有权唯一** | 每个数据实体只有一个系统拥有写权限，其他系统只读引用 | "谁管什么数据，谁就管什么逻辑" |

### 为什么这样设计

当前项目的核心问题是审单编排的同步长链路：`approve()` 同步调 5 个服务，全部成功才返回，任何一步失败要写复杂的 try-catch 补偿。目标架构把 billing 和 fulfillment 从同步 Feign 调用改为异步事件消费，审单方法只需要同步调 3 个子域（customer/inventory/marketing），成功后发 Kafka 事件即可返回。

## 三、四大系统职责边界

### 系统一：库存中心（tribunal-inventory-center）

| 维度 | 说明 |
|------|------|
| **定位** | 上游数据集成 + 全渠道库存视图 |
| **端口** | 8090 |
| **数据库** | `tribunal_inventory_center`（合并现有 inventory + inventory_push） |
| **核心实体** | InventoryItem（库存主数据）、InventoryBatch（批次）、InventoryFlow（流水） |
| **上游** | 外部 ERP/WMS（HTTP/MQ/SFTP 推送库存数据） |
| **下游** | OMS（Feign 同步：可售查询/预占/释放） |

**关键能力**：
- 接收上游推送的库存数据（幂等去重）
- 多维度库存管理（总/可用/锁定/在途/预留）
- 可售库存计算（总 - 锁定 - 预留 - 安全库存）
- 库存预占/释放（供 OMS 审单时调用）
- 批次/效期管理（FIFO/FEFO）
- 库存变动流水（审计追溯）

### 系统二：订单中台（tribunal-oms）

| 维度 | 说明 |
|------|------|
| **定位** | 交易核心——订单全生命周期管理 |
| **端口** | 8080 |
| **数据库** | `tribunal_oms`（合并现有 order + customer + inventory + marketing） |
| **核心实体** | Order（订单聚合根）、Customer（客户）、CreditLimit（信用）、PriceRule（价格） |
| **上游** | 库存中心（Feign 同步）、渠道网关（HTTP 接单） |
| **下游** | 履约系统（Kafka 异步）、金融结算（Kafka 异步） |

**关键能力**：
- 订单创建（多渠道接入标准化）
- 审单编排（信用校验→库存预占→价格计算→状态迁移）
- 订单状态机（状态守卫幂等）
- 拆单/合单（按仓库/商家/配送方式拆分）—— **待实现**
- 寻源分仓（最优仓库选择）—— **待实现**
- 信用额度管理（占用/释放/恢复）
- 价格/促销/折扣计算
- 订单状态回传（接收下游事件，驱动状态机）

**内部子域通信**：
- OMS → customer 子域：Feign 同步（信用校验/占用）
- OMS → inventory 子域：Feign 同步（可售查询/预占）
- OMS → marketing 子域：Feign 同步（价格计算/促销）
- 这三个子域在同一个进程内，不经过网络，不存在跨服务调用开销

### 系统三：履约系统（tribunal-fulfillment）

| 维度 | 说明 |
|------|------|
| **定位** | 履约执行——从审单通过到签收完成 |
| **端口** | 8085 |
| **数据库** | `tribunal_fulfillment` |
| **核心实体** | FulfillmentOrder（履约单）、FulfillmentLine（明细）、FactoryOrder（工厂指令） |
| **上游** | OMS（Kafka 异步：消费 OrderApprovedEvent） |
| **下游** | OMS（Kafka 异步：发布 OrderShippedEvent/OrderDeliveredEvent） |

**关键能力**：
- 消费审单通过事件，创建履约单
- 履约任务编排（DAG：拣货→复核→打包→出库→发运→签收）
- 发货/签收状态回传（发布事件给 OMS）
- 工厂指令下发
- 部分发货处理
- 履约异常处理

### 系统四：金融结算（tribunal-settlement）

| 维度 | 说明 |
|------|------|
| **定位** | 资金结算——计费、扣款、分账、对账 |
| **端口** | 8082（BMS）/ 8083（FMS） |

- FMS：退款/冲正（原路退回，分账回退）
- FMS：对账（与支付渠道/订单/库存日终对账）

## 四、通信模式矩阵

| 调用路径 | 方式 | 协议 | 理由 |
|----------|------|------|------|
| OMS → customer 子域 | 同步 | 进程内方法调用 | 同进程，无网络开销 |
| OMS → inventory 子域 | 同步 | 进程内方法调用 | 同上 |
| OMS → marketing 子域 | 同步 | 进程内方法调用 | 同上 |
| OMS → inventory-center | 同步 | Feign (HTTP) | 可售库存/预占必须实时确认 |
| OMS → fulfillment | **异步** | Kafka: `order-events` | 审单通过后发事件，不等履约创建 |
| OMS → settlement (BMS) | **异步** | Kafka: `order-events` | 审单通过后发事件，不等账单生成 |
| fulfillment → OMS | **异步** | Kafka: `fulfillment-events` | 发货/签收状态回传 |
| fulfillment → settlement | **异步** | Kafka: `fulfillment-events` | 签收后触发结算 |
| settlement → OMS | **异步** | Kafka: `settlement-events` | 结算完成回传 |
| inventory-center → OMS | **异步** | Kafka: `inventory-events` | 库存变化通知 |

### 同步 vs 异步决策树

```
调用需要立即拿到结果吗？
├── 是 → 调用失败时主流程必须阻断吗？
│   ├── 是 → Feign 同步调用（如：信用校验、库存预占）
│   └── 否 → Feign 同步 + 降级 fallback（如：通知发送）
└── 否 → Kafka 异步事件（如：账单生成、履约创建、状态回传）
```

## 五、事件契约定义

所有跨系统事件定义在 `tribunal-common-event` 模块中，所有系统共享。

### 事件清单

| 事件类 | Topic | 发布方 | 消费方 | 触发时机 | 关键字段 |
|--------|-------|--------|--------|----------|----------|
| `OrderApprovedEvent` | `order-events` | OMS | Fulfillment, Settlement-BMS | 审单通过 | orderId, orderNo, customerId, items[], totalAmount |
| `OrderRejectedEvent` | `order-events` | OMS | Notification | 审单拒绝 | orderId, rejectReason |
| `OrderCancelledEvent` | `order-events` | OMS | Fulfillment, Settlement | 订单取消 | orderId, cancelReason |
| `OrderShippedEvent` | `fulfillment-events` | Fulfillment | OMS, Settlement | 已发货 | orderId, fulfillmentId, carrierCode, trackingNo, shippedAt |
| `OrderDeliveredEvent` | `fulfillment-events` | Fulfillment | OMS, Settlement | 已签收 | orderId, fulfillmentId, signedAt, signedBy |
| `SettlementCompletedEvent` | `settlement-events` | Settlement | OMS | 结算完成 | orderId, settlementId, settledAmount |
| `InventoryChangedEvent` | `inventory-events` | Inventory Center | OMS | 库存变化 | skuCode, warehouseId, availableQty |

### 事件设计规范

```java
// 所有事件继承基类
public abstract class DomainEvent {
    private String eventId;          // UUID，幂等去重用
    private String eventType;        // 事件类型枚举
    private LocalDateTime occurredAt; // 发生时间
    private String traceId;          // 链路追踪ID
}

// 具体事件示例
public class OrderApprovedEvent extends DomainEvent {
    private String orderId;
    private String orderNo;
    private String customerId;
    private List<OrderItemSnapshot> items;
    private BigDecimal totalAmount;
    private BigDecimal payableAmount;
}
```

### 事件消费规范

- **幂等**：消费者必须用 `eventId` 去重，重复消费不产生副作用
- **重试**：消费失败自动重试 3 次，间隔递增（1s/5s/30s）
- **死信**：重试超限后投递到 `xxx-events.DLT` 死信 topic
- **顺序**：同一 orderId 的事件必须顺序消费（Kafka partition by orderId）

## 六、Maven 依赖规则

### 依赖方向（严格单向）

```
tribunal-common-core       ← 所有模块都依赖
tribunal-common-event      ← 所有可部署系统都依赖
tribunal-common-starter    ← 所有可部署系统都依赖

tribunal-oms               → tribunal-common-*, tribunal-inventory-center-api（Feign 接口）
tribunal-fulfillment       → tribunal-common-*（不依赖 tribunal-oms！）
tribunal-settlement        → tribunal-common-*（不依赖 tribunal-oms！不依赖 tribunal-fulfillment！）
tribunal-inventory-center  → tribunal-common-*
tribunal-auth              → tribunal-common-*
```

### 禁止的依赖

| 禁止 | 原因 |
|------|------|
| fulfillment → oms | 履约系统不应知道订单领域的代码 |
| settlement → oms | 结算系统不应知道订单领域的代码 |
| settlement → fulfillment | 结算和履约是平级下游，不应互相依赖 |
| oms → fulfillment | OMS 只通过事件与履约通信，不直接调用 |
| oms → settlement | OMS 只通过事件与结算通信 |
| 任何模块 → 具体实现模块 | 只依赖 API 接口模块，不依赖实现 |

### Feign 接口模块分离

对于需要 Feign 同步调用的场景（如 OMS → inventory-center），将 Feign 接口抽到独立的 API 模块：

```
tribunal-inventory-center/
├── tribunal-inventory-center-api/       # Feign 接口 + DTO（OMS 依赖这个）
├── tribunal-inventory-center-push/      # 上游数据接入实现
└── tribunal-inventory-center-core/      # 库存核心实现（启动模块）
```

OMS 的 pom.xml 只依赖 `tribunal-inventory-center-api`，不依赖 `core`。

### 分层依赖规则

```
api → application → domain ← infrastructure
                        ↑
                 infrastructure 实现 domain 的接口
```

- **domain**：零框架依赖，纯 Java。不允许出现 Spring/MyBatis/JPA 注解
- **application**：依赖 domain，编排用例，管理事务边界。不直接操作数据库
- **infrastructure**：依赖 domain（实现 Repository 接口）+ application（实现事件发布接口）。包含所有技术细节
- **api**：依赖 application + infrastructure。是唯一可启动的模块（含 main 方法）

## 八、技术选型

| 维度 | 当前 | 目标 | 理由 |
|------|------|------|------|
| 框架 | Spring Boot 3.2.x | 保持 | 稳定成熟，生态完整 |

| 缓存 | 无 | Redis | 分布式幂等 + 登录失败锁定 + Refresh Token 存储 |
| 熔断降级 | 无 | Resilience4j | Feign 熔断/降级/限流 |
| 服务发现 | 无 | Nacos | 服务注册发现 + 配置中心 |
| API 网关 | 无 | Spring Cloud Gateway | 统一入口/路由/限流 |
| 分布式事务 | 无 | 本地消息表 + Saga | 最终一致性，不用 2PC |
| 数据库 | MySQL（每服务独立库） | 保持 | 数据隔离 |
| 连接池 | HikariCP（默认） | HikariCP（调优） | 显式配置池大小 |
| ID 生成 | UUID | 雪花算法（Snowflake） | 趋势递增，利于索引 |

## 九、审单编排改造对比

### 当前（同步长链路）

```java
// OrderReviewApplicationService.approve()
public void approve(ApproveCommand cmd) {
    // ① 信用校验（Feign → customer-service）
    customerFeignClient.checkCredit(cmd.getCustomerId(), cmd.getAmount());
    // ② 价格计算（Feign → marketing-service）
    marketingFeignClient.calculatePrice(cmd.getSkus());
    // ③ 库存预占（Feign → inventory-service）
    inventoryFeignClient.reserve(cmd.getSkus());
    try {
        // ④ 生成账单（Feign → billing-service）  ← 同步等待
        billingFeignClient.generateBill(cmd);
        // ⑤ 创建履约（Feign → fulfillment-service）  ← 同步等待
        fulfillmentFeignClient.createFulfillment(cmd);
    } catch (Exception e) {
        // 补偿：释放库存 + 释放信用（但账单/履约补偿不完整！）
        inventoryFeignClient.release(cmd.getSkus());
        customerFeignClient.releaseCredit(cmd.getCustomerId(), cmd.getAmount());
        throw e;
    }
    // ⑥ 状态迁移
    order.confirm();
    // ⑦ 发通知（Feign → notification-service）
    notificationFeignClient.send(cmd);
}
```

**问题**：步骤④⑤同步等待拖长 RT；失败补偿不完整；编译时依赖 billing/fulfillment 代码。

### 目标（同步短链路 + 异步事件）

```java
// OrderReviewApplicationService.approve()
@Transactional
public void approve(ApproveCommand cmd) {
    // ① 信用校验（进程内调用 customer 子域）
    customerDomainService.checkAndOccupyCredit(cmd.getCustomerId(), cmd.getAmount());
    // ② 价格计算（进程内调用 marketing 子域）
    marketingDomainService.calculatePrice(cmd.getSkus());
    // ③ 库存预占（Feign → inventory-center，唯一跨服务同步调用）
    inventoryCenterFeignClient.reserve(cmd.getSkus());

    try {
        // ④ 状态迁移
        order.confirm();

        // ⑤ 发布审单通过事件（本地消息表保证原子性）
        //    → Fulfillment 消费后创建履约单
        //    → Settlement-BMS 消费后生成账单
        orderEventPublisher.publish(OrderApprovedEvent.of(order));

    } catch (Exception e) {
        // 补偿：释放库存 + 释放信用（只需补偿同步步骤）
        inventoryCenterFeignClient.release(cmd.getSkus());
        customerDomainService.releaseCredit(cmd.getCustomerId(), cmd.getAmount());
        throw e;
    }
}
```

**改进**：
- 步骤④⑤从同步 Feign 改为异步 Kafka 事件，方法立即返回
- 补偿只需回滚同步步骤（信用+库存），异步步骤失败可重试
- 编译时不依赖 fulfillment/billing 的代码，只依赖 `common-event` 的事件类
